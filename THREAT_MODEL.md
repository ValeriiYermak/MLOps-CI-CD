# Threat Model (C6)

Модель загроз для inference-сервісу та MLOps-платформи в цілому.
Формат: STRIDE-подібний, 5 найбільш релевантних загроз для цього
проєкту (локальний kind-кластер, публічний inference-endpoint,
Model Registry з promotion workflow).

---

## 1. Ін'єкція некоректних/шкідливих вхідних даних у `/predict`

**Опис загрози:** зловмисник (або помилковий клієнт) надсилає на
inference-endpoint дані поза очікуваним діапазоном, некоректного типу,
або зловмисно сформований payload з метою викликати помилку сервера,
витік внутрішньої інформації через traceback, або DoS через ресурсоємну
обробку.

**Вплив:** середній — можлива відмова сервісу (крашпод), витік
внутрішніх деталей реалізації через повідомлення про помилку.

**Контрзахід (реалізовано — C1):** Pydantic-схема (`inference/app/schemas.py`)
валідує кожне поле (`sepal_length`, `sepal_width`, `petal_length`,
`petal_width`) з обмеженнями `gt=0, le=15`, строгою типізацією.
Кастомний `RequestValidationError`-хендлер повертає HTTP 400 з переліком
некоректних полів, без внутрішніх деталей стеку/реалізації.

---

## 2. Зловживання ресурсами через масовий потік запитів (DoS/DDoS)

**Опис загрози:** зловмисник надсилає велику кількість запитів до
`/predict` за короткий проміжок часу з метою вичерпати обчислювальні
ресурси пода (CPU/memory) або зробити сервіс недоступним для легітимних
користувачів.

**Вплив:** високий — повна відмова inference-сервісу, каскадний вплив
на обидва Blue-Green slot, якщо атака триває довго.

**Контрзахід (реалізовано — C2):** rate limiting 30 запитів/хвилину на
`/predict` через `slowapi`, застосовується на рівні кожного пода
окремо. Обмеження: rate limiting не централізований (кожен под лічить
незалежно), тому реальна допустима межа для клієнта — до
`30 × кількість Ready-подів` за slot. Для production-масштабу
знадобився б централізований rate limiter (напр. на рівні Ingress/API
Gateway) — задокументовано як обмеження поточної реалізації.

---

## 3. Підміна або деградація моделі в Model Registry (supply chain)

**Опис загрози:** зловмисник (або помилка процесу) підміняє артефакт
моделі в MinIO/S3 після реєстрації в MLflow, або промоутить у Production
непроверену/шкідливу версію моделі без належного контролю.

**Вплив:** високий — inference-сервіс почне видавати результати
скомпрометованої/зіпсованої моделі всім клієнтам без видимих ознак
збою (silent failure).

**Контрзахід (реалізовано — C4):** SHA256-checksum обчислюється при
реєстрації кожної версії моделі й зберігається як immutable
MLflow-тег (`sha256_checksum`). `model_loader.py` перераховує checksum
артефакту **перед** завантаженням і відмовляється завантажувати модель
за невідповідності або відсутності тегу — реально спрацювало один раз
у процесі розробки, коли под відмовився завантажити версію без
checksum-тегу (модель, зареєстровану до впровадження C4).

**Залишковий ризик:** checksum захищає від зміни артефакту *після*
реєстрації, але не від навмисної реєстрації шкідливої моделі *під час*
тренування — це покривається окремим контролем (RBAC, п.4 нижче) та
процесом рев'ю перед промоушеном.

---

## 4. Несанкціонований доступ до Model Registry / production-namespace

**Опис загрози:** користувач без належних прав отримує можливість
промоутнути невалідовану модель у Production, видалити версії з
Registry, або змінити конфігурацію production-подів напряму.

**Вплив:** високий — обхід усього promotion workflow, потенційна
підміна моделі без audit trail.

**Контрзахід (реалізовано — C3):** RBAC-ролі в `rbac/`:
`mlops-engineer` має повний доступ до `staging` namespace, але
обмежений (без delete/secrets/RBAC-редагування) доступ до `production`;
`viewer` — read-only ClusterRole для всіх namespace. Промоушен/rollback
виконуються виключно через контейнеризовані K8s Jobs (не пряме
редагування MLflow Registry вручну), що додатково обмежує поверхню
атаки до конкретного, аудованого шляху дій.

**Залишковий ризик:** у поточному kind-кластері немає реальної системи
автентифікації користувачів (SSO/OIDC) — RoleBinding у `rbac/`
використовують плейсхолдер-Users для демонстрації принципу. У
production-кластері знадобилась би інтеграція з реальним identity
provider.

---

## 5. Втрата audit trail / неможливість розслідувати інцидент

**Опис загрози:** після інциденту (наприклад, помилкового промоушену
поганої моделі) неможливо встановити, хто/коли/яку дію виконав, що
унеможливлює розслідування та належну відповідальність.

**Вплив:** середній (непрямий) — не спричиняє інцидент сам по собі, але
критично ускладнює реакцію та запобігання повторенню.

**Контрзахід (реалізовано — C5):** promote/rollback запускаються
виключно як K8s Jobs, чий stdout автоматично збирається Promtail і
пересилається в Loki. Кожна дія логує структурований рядок з префіксом
`AUDIT:`, що включає версію моделі, дію (promote/rollback), часову
мітку. Перевірено робочим через прямий запит до Loki API
(`query_range`), знайдено обидва типи audit-записів з коректними
лейблами (`app=mlflow-registry-ops`, `namespace=mlops-system`).

**Залишковий ризик:** Loki в цьому проєкті використовує `emptyDir`
(без persistence) — audit-логи не переживають повний rebuild кластера.
Для production знадобилось б зовнішнє, довготривале сховище логів.
