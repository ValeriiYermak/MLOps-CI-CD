# Звіт: порівняння fat vs slim Docker-образів для ML inference

## Порівняльна таблиця

| Метрика                  | Fat image (`ml-infer-fat:1.0`)       | Slim image (`ml-infer-slim:1.0`)      |
|---------------------------|---------------------------------------|----------------------------------------|
| Розмір image               | 2.85 GB                              | 1.4 GB                                 |
| Кількість шарів             | 16                                    | 16                                      |
| Час збірки (орієнтовно)     | ~15-20 хв                            | ~10-15 хв                               |
| Inference результат          | top-3 збігається                     | top-3 збігається                        |
| Найважчий шар                | `RUN pip install ...` (963 MB)        | `COPY /root/.local` (953 MB)            |
| Системний build-шар          | `RUN apt-get ...` build-essential (694 MB) | відсутній (винесено в builder-стадію) |
| Базовий Debian-шар            | `debian.sh` (134 MB)                  | `debian.sh` (87.4 MB)                   |
| Зайві інструменти             | Компілятори, build-essential, apt-кеш | Мінімізовано (лише runtime-залежності)  |

## Методологія перевірки

Обидва образи запускались з переданим bind-mount `example.jpg`:

docker run --rm -v ${PWD}/example.jpg:/app/example.jpg ml-infer-fat:1.0
docker run --rm -v ${PWD}/example.jpg:/app/example.jpg ml-infer-slim:1.0

Результат в обох випадках ідентичний:

Top-3 передбачення для 'example.jpg':

1. class_id=258, confidence=0.3091
2. class_id=259, confidence=0.0510
3. class_id=261, confidence=0.0159

## Висновок

### Що було зайвим у fat-образі

1. **Базовий образ `python:3.13`** (не slim) містить повний набір build-tools: компілятор `gcc`, `build-essential`, dev-заголовки бібліотек — усе це потрібне лише для *компіляції* пакетів під час встановлення, а не для *виконання* готового inference-коду. У `docker history` це видно як окремий шар `RUN apt-get ...` вагою **694 MB**, якого повністю немає в slim-образі.
2. **`COPY . .` перед `pip install`** — увесь контекст репозиторію (включно з `.git`, якби `.dockerignore` не спрацював) копіювався одним шаром до встановлення залежностей, що також ламає ефективне кешування шарів Docker: будь-яка зміна коду інвалідує кеш `pip install` і змушує перевстановлювати torch (~1 ГБ) з нуля при кожному білді.
3. **Відсутність multi-stage** — тимчасові файли самого процесу встановлення пакетів (кеш pip, проміжні артефакти компіляції нативних розширень) залишаються в фінальному образі, бо весь білд відбувається в одній стадії.

### Що змінилося в slim

1. **Multi-stage build** — виконання `pip install --user` винесено в окрему `builder`-стадію на базі `python:3.13-slim`. У фінальний `runtime`-образ копіюється лише результат (`/root/.local`, вже встановлені пакети), без компіляторів і без кешу pip, які існували тільки тимчасово в проміжній стадії.
2. **Базовий образ `python:3.13-slim`** — легший Debian-дистрибутив без зайвих системних утиліт: сам базовий шар (`debian.sh`) на **46.6 MB** легший, ніж у fat-версії.
3. **Точкове копіювання** (`COPY app/`, `COPY model/`, `COPY example.jpg`) замість `COPY . .` — у фінальний образ гарантовано не потрапляють файли на кшталт `README.md`, `report.md`, `install.log`, які не потрібні для inference.
4. **Порядок інструкцій** (`COPY requirements.txt` окремо від коду) — забезпечує ефективніше кешування шарів: зміна коду в `app/` більше не інвалідує кеш встановлених залежностей.

Сумарна економія розміру образу: **2.85 GB → 1.4 GB, приблизно 51%**.

### Чи змінився inference

Ні. Результат top-3 передбачень (`class_id` та `confidence`) повністю ідентичний в обох образах — оптимізація образу торкається лише складу файлової системи контейнера, а не логіки чи середовища виконання Python-коду.

### Пропозиції для подальшої оптимізації

1. **Прибрати CUDA-залежності повністю з requirements.txt**, а не лише перенаправити на CPU-індекс — можна явно вказати `torch==2.7.0+cpu` разом з `--index-url https://download.pytorch.org/whl/cpu` для гарантії, що навіть при зміні джерела пакет не підтягне GPU-залежності повторно.
2. **Використати `--no-install-recommends`** при можливих майбутніх `apt-get install` кроках, якщо знадобляться додаткові системні бібліотеки для image-processing (наприклад, `libjpeg`, `libpng` для Pillow) — це вже мінімізований базовий набір без рекомендованих, але не обов'язкових пакетів.
3. **Розглянути дистрибуцію моделі окремо від образу** (наприклад, завантаження `model.pt` при старті контейнера з S3/artifact-registry, а не запікання у сам образ) — це дозволяє оновлювати модель без пересбирання образу.
4. **ONNX Runtime замість повного torch runtime** — якщо inference не потребує повної гнучкості PyTorch, перехід на `onnxruntime` (значно легша бібліотека, без залежності від `torch` у runtime) міг би скоротити розмір образу ще суттєвіше — це вже вихід за межі TorchScript, згаданий у завданні як напрямок для подальшого розвитку.
