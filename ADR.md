# ADR: вибір стратегії деплою та ключові архітектурні рішення

**Статус:** Прийнято
**Дата:** День 3 фінального проєкту (деплой-стратегія), доповнено День 5

## Контекст

Технічне завдання вимагає обрати одну стратегію деплою моделі з трьох:
Canary (90/10), Blue-Green, або A/B-тестування — і обґрунтувати вибір.
Проєкт виконується в межах 5-денного часового бюджету, локально на kind
(AWS-акаунт обмежений t3.micro, недостатньо ресурсів для повного стеку).

## Рішення: Blue-Green deployment

Обрано Blue-Green замість Canary чи A/B.

### Обґрунтування

1. **Простота реалізації відповідає часовому бюджету.** Blue-Green —
   два повністю ізольовані Deployment (`inference-blue`, `inference-green`)
   і перемикання трафіку через зміну `selector` в одному Service. Canary
   потребує додаткової інфраструктури для поступового розподілу трафіку
   (weighted routing — Istio/Linkerd service mesh, або хоча б Nginx
   Ingress з canary-анотаціями), що в межах kind-кластера і 5 днів є
   невиправданим ризиком.

2. **Мінімальна вимога — просте, повністю робоче рішення краще за
   складне недороблене.** Це прямо сформульовано ментором як один з
   топ-5 пасток проєкту: "проста робоча версія (наприклад Blue-Green)
   оцінюється вище за складну недороблену (Canary)". Враховуючи, що
   значна частина часового бюджету вже пішла на подолання інфраструктурних
   перешкод (deprecated Bitnami charts, WSL2-ліміти пам'яті, Loki chart
   з зайвим Operator, ArgoCD/Prometheus баги під час rebuild) — вибір
   Canary поставив би під загрозу завершення security- та
   документаційних вимог (Блоки C, D).

3. **Blue-Green дає найвищу гарантію коректного rollback.** Оскільки
   обидва slot (blue/green) — повністю окремі Deployment із власним
   `_model_watcher`, відкат — це або перемикання `selector` назад, або
   (у поточній реалізації) rollback моделі через MLflow Registry
   (Archived → Production), яку обидва slot підхоплюють автоматично.
   Canary з поступовим збільшенням ваги трафіку ускладнює момент
   "миттєвого повного відкату" — потрібно синхронно змінювати ваги на
   всіх точках маршрутизації.

4. **Достатньо для навчальної демонстрації принципу.** Мета завдання —
   продемонструвати розуміння концепції zero-downtime deployment і
   promotion workflow, а не побудувати production-grade traffic-shaping
   систему. Blue-Green покриває це повністю: nova модель розгортається
   в неактивний slot, перевіряється (`/health`), і трафік перемикається
   одним атомарним кроком.

## Trade-offs (свідомо прийняті)

| Trade-off | Наслідок | Чому прийнятно тут |
|---|---|---|
| Немає поступового/часткового переходу трафіку | Неможливо перевірити нову модель на невеликому % реального трафіку перед повним перемиканням | Для навчального проєкту з синтетичним Iris-датасетом реальний production-трафік відсутній; ризик прийнятний |
| Подвійне споживання ресурсів (обидва slot завжди `Running`) | На реальному EKS з t3.micro це було б проблемою (обмеження ~4 пода/нода) | На kind-кластері немає жорсткого ліміту подів/ноду — не є вузьким місцем |
| Немає автоматичного canary-аналізу метрик перед повним перемиканням | Рішення про перемикання приймається вручну (людина дивиться на Grafana/`/health`), а не автоматично за SLO | Прийнятно для 5-денного навчального проєкту; для production знадобився б окремий compontent (напр. Argo Rollouts + Prometheus-аналіз) |
| `MinIO`/`PostgreSQL` на `emptyDir` (не PVC) | Повний rebuild кластера знищує Model Registry | Свідомий resource-saving trade-off — не потрібен EBS CSI/PVC для навчального kind-кластера; задокументовано в README/RUNBOOK, процедура відновлення відпрацьована й перевірена практично двічі |

## Альтернативи, які розглядались і чому відхилені

- **Canary (90/10):** відхилено з причин 1-2 вище — потребує service
  mesh або Ingress-level traffic splitting, що додає інфраструктурний
  компонент, невиправданий у межах бюджету.
- **A/B-тестування:** відхилено — A/B зазвичай передбачає паралельне
  порівняння метрик двох версій за критерієм бізнес-результату (не
  просто технічної коректності), що виходить за межі обсягу задачі
  (модель тут — навчальний Iris-класифікатор, немає бізнес-метрики для
  порівняння).

## Deprecated API, використаний свідомо

`MlflowClient.transition_model_version_stage()` позначений deprecated
з MLflow 2.9.0 (MLflow рухається у бік Model Registry без "stages",
на систему aliases/tags). У цьому проєкті API все ще використовується,
оскільки:
- він повністю функціональний на використаній версії MLflow (`3.15.1`)
- вимога завдання явно сформульована в термінах stages (`Staging` →
  `Production` → `Archived`), що напряму відповідає семантиці цього API
- міграція на aliases зайняла б додатковий час без функціональної
  переваги для обсягу цього проєкту

**Що зробили б інакше з більшим часовим бюджетом:** мігрували б на
`MlflowClient.set_registered_model_alias()` + tags замість stages,
що є рекомендованим MLflow шляхом наперед і уникло б залежності від
API, який буде повністю видалено в майбутньому мажорному релізі.

## Інші архітектурні рішення, що виникли по ходу проєкту (коротко)

- **Локальний kind замість AWS EKS** — офіційно узгоджений з ментором
  fallback через обмеження AWS-акаунта (тільки t3.micro). Детальний
  мапінг компонентів — у README.md.
- **Plain Kubernetes-манифести замість Helm chart для MinIO, PostgreSQL,
  Loki** — усі три офіційні chart'и виявились непридатними для цього
  проєкту з різних причин (Bitnami deprecated, Loki chart тягне зайвий
  Operator з CRD-конфліктами) — обрано простіші, повністю контрольовані
  plain-манифести замість боротьби з чужою складністю chart'ів.
- **Promote/Rollback як контейнеризовані K8s Jobs, а не host-скрипти** —
  для довіреного, відтворюваного audit trail (C5): stdout поду
  автоматично потрапляє в Loki через Promtail, тоді як виконання скрипта
  напряму з хоста не залишає централізованого сліду.
- **Port-forward замість Ingress** для доступу до MLflow/Grafana/ArgoCD
  UI — обрано через простоту для локального одноосібного проєкту; для
  production знадобився б Ingress Controller + TLS.
